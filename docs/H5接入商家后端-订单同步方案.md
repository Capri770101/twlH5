# H5 接入商家后端 · 订单同步方案

> 勘查时间：2026-09-18｜勘查对象：`129.204.85.139` 上的 `/opt/flower-shop`（端口 3456，即 `aistore.xiangbinmeigui.com`）
> 目标：**打通 H5 订单，确保订单能送到商家手里**（范围收窄，不含支付交接与商家系统改造）
> 修订：v2，更正 v1 中关于"商家后端会重算商品单价"的错误判断（见 §2.1）

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| H5 订单现在送到哪了？ | **哪也没去。** 只落在 H5 自己的库 `h5_shop.orders`，商家完全不知道（§1.1） |
| 能不能同步给商家？ | **能**，且商家后端已自带完整订单管道与商家通知机制 |
| 需要新建同步中间件吗？ | **不需要**。订单表、状态机、履约分派、企业微信通知都已存在 |
| 商家怎么"收到"订单？ | ① 企业微信群机器人实时推送 ② 商家后台 `/admin` 订单列表 ③ 分派到门店的 SaaS 平台 |
| 改动量 | H5 侧：中等（服务端桥接 + 状态回捞 + 退款审核）。商家后端：小改（见 §6） |
| 最大风险 | **满减规则两边不一致 → 金额对不上；以及退款可能被两个系统各退一次** |

**一句话方案**：H5 保留自己的收款（技术上是必须的，见 §2.2），支付成功后由 H5 服务端把订单**投递**进商家后端的订单管道；商家接单/制作/配送的状态再**回捞**回 H5 展示。

## 1. 现场事实（已实测，非推测）

### 1.1 H5 订单目前的真实去向

**结论：一笔都没到商家手里。**

| 检查项 | 实测结果 |
|---|---|
| H5 订单存放 | `h5_shop.orders` @3307（本机独立 MySQL 实例），**全部订单只有 2 笔，都是测试单**（各 ¥1.00，状态 `refunded` / `cancelled`） |
| 商家库里的 H5 订单 | `flower_shop.orders` 中订单号以 `T` 开头（H5 格式）的记录数 = **0** |
| H5 后端有无通知商家的代码 | `grep qyapi\|webhook\|3456` → **0 处**。H5 后端与商家后端之间**没有任何连接** |
| 商家有无收到过 H5 订单通知 | 无。企业微信 webhook 只由商家后端在订单支付成功时触发，而 H5 订单从未进入商家后端 |
| 分派到门店 | 无。`danceOrchidSync` 只对商家库里的订单生效 |

> ⚠️ **业务含义**：现在用户在 H5 下单付款，钱进了服务商号，但**花店根本收不到这个单**。支付成功之后没有任何履约动作 —— 这是当前最大的业务断裂，也是本次要解决的问题。

### 1.2 这个后端不是"商品接口"，是一套完整的多角色业务系统

之前我们只把它当成 H5 的商品数据源（`/v1/flowers/list` 等）。实际它同时提供三套角色接口：

| 角色 | 路径前缀 | 代表接口 |
|---|---|---|
| 客户端（小程序 / 未来 H5） | `/v1/orders/*`、`/v1/flowers/*`、`/v1/auth/*` | `orders/create`、`orders/pay-prepare` |
| 商家端（商家后台 `admin/`） | `/v1/merchant/*` | `merchant/orders`、`merchant/order/status`、`order/refund-approve` |
| 总部端 | `/v1/headquarters/*` | `headquarters/orders`、`stores`、`dashboard` |

数据库 `flower_shop`@3306（本机）已有 **`orders` 表（112 条真实订单）**：

```
id(主键) / shop_id / status / status_text / customer_name / customer_phone
total_price(分) / items(json) / address(json) / raw(json 完整对象) / create_time
索引：idx_orders_shop_time(shop_id, create_time)、idx_orders_status(status)
```

**价格量纲已核实：`products.price` 为 INT「分」**（如 `8800` = ¥88），与 H5 完全一致，**无 100 倍风险**。

### 1.3 订单状态机（与 H5 现有的完全可对齐）

```
new 待支付 → pending 待接单 → paid 已接单 → making 制作中 → delivering 配送中 → completed 已完成
        ↘ cancelled 已取消          ↘ refunding → refunded / refund_failed
```

### 1.4 订单管道里已经挂着两个下游（这才是「同步给商家」的真相）

商家后端在订单**支付成功**时（`pay-notify` 或 `pay-success`）会触发两件事：

**下游① 分派给门店 —— 真正的履约通道**
`syncOrderToDanceOrchid()` → `POST https://xcx.xiangbinmeigui.com/api/Platform/Take`
参数：`appid` + `act=AddOrder` + `timestamp` + `nonce` + `data`(订单 JSON) + `sign`(MD5：键名排序拼 `k=v&` 后接 `secret=`)。
逐店凭证（`rsid`/`appid`/`secret`）来自 `/opt/flower-shop/order-integration.json`，**已配置 13 家门店**。
仅当状态 ∈ `pending/paid/making/delivering/completed` 才推送；已成功不重推；结果落库到 `order.danceOrchidSync`（含 `externalOrderId`）。
**线上实测：34 笔已成功同步。**

**下游② 通知商家 —— 企业微信群机器人**
`scheduleWecomOrderNotification()` → `qyapi.weixin.qq.com/cgi-bin/webhook/send`，把订单信息实时推到商家群。

> 🔑 **只要 H5 的订单能进入这个后端，商家「收到订单」这件事就自动完成了** —— 不需要我们再开发任何通知机制。

### 1.5 对 H5 有利的现成条件

- **同机部署**：H5 后端（`twlh5-api`:4000）与商家后端（`:3456`）在**同一台服务器**，服务端调 `127.0.0.1:3456` 即可，无跨域、无公网延迟、无需开白名单。
- **只读回捞无需鉴权**：`GET /v1/orders/detail?id=`、`/v1/orders/list`、`/v1/orders/batch` 都不校验登录（只过滤 `customerHidden`）→ H5 可随时把商家状态读回来。
- **门店支付配置齐全**：12 家店 `subMchId` 全部配好（s001 `1746109516` … s016 `1117227450`），状态均 `open`。
- **门店归属/同城/每日单号**：`normalizeOrderItemsForShop()` 已实现"一次一店""跨城拦截""门店休息拦截""按店按日流水号"。

## 2. 三个阻塞点（必须先拍板）

### ✅ 2.1 满减规则两边不一致 —— 金额对不上（附 v1 判断更正）

> **更正说明**：v1 文档我写的是"商家后端不信前端传的价，回自己库查价重算"。**这个判断是错的**，已实地复核代码更正如下。

**商家后端不会改动商品单价。** 它的 `normalizeOrderItemsForShop()` 用展开语法保留了请求里的价格：

```js
normalizedItems.push({
  ...item,                 // ← price / quantity / name 都原样保留
  id: product.id,
  shopId: shop.id,
  shopName: shop.name || '',
  ...
});
// 随后按请求里的价计价
const goodsTotalPrice = orderItems.reduce(
  (sum, item) => sum + (Number(item.price || 0) * Number(item.quantity || 1)), 0);
```

查商品 id 只用于三件事：**校验商品存在、校验 `stock > 0`、校验门店归属**。所以单价、数量都不会变。

**真正的问题是：它会在总价上再叠加一层自己的满减，而且档位和 H5 不一样。**

```js
// 商家后端 server.js : calcFullReduction（单位：分）
if (amount >= 30000) return 3000;   // 满 ¥300 减 ¥30
if (amount >= 20000) return 2000;   // 满 ¥200 减 ¥20
if (amount >= 10000) return 1000;   // 满 ¥100 减 ¥10

// H5 server/src/orders.js:175 —— 只有一档
const discount = itemTotal >= 20000 ? 2000 : 0;   // 仅 满 ¥200 减 ¥20
```

**对照结果：**

| 商品小计 | H5 实收 | 商家后台显示 | 差异 |
|---|---|---|---|
| ¥100 ~ ¥199.99 | 原价 | **少 ¥10** | ⚠️ 不一致 |
| ¥200 ~ ¥299.99 | 减 ¥20 | 减 ¥20 | ✅ 一致 |
| ≥ ¥300 | 减 ¥20 | **多减 ¥10** | ⚠️ 不一致 |

**为什么这件事必须解决**（不只是"数字看着不一样"）：
- 商家后台的「同意退款」是按**它自己的 `totalPrice`** 发起微信退款的 → **退款金额会多退或少退**
- 两边**退款单号规则不同**：商家用 `'RF' + 订单号`，H5 用 `'R' + 订单号` → 两个系统各退一次就是**两笔独立出账**
- 分账基数也会不一致

**最小改动方案（推荐，不用对方改代码）**：把 H5 的满减改成与商家后端**完全一致的三档**，并加一道**推单后金额校验** —— 投递完回读商家订单的 `totalPrice`，与 H5 实付不一致就告警并阻止进入履约。
理由：H5 现在"只有满 200 减 20"本身就是不完整的促销实现，对齐三档等于顺带把促销做完整。

备选：请同事支持「以外部传入金额为准」，但对方要改代码且需防刷。

**另一处需注意**：`isProductAvailableForSale()` 要求 `stock > 0`。实测商家库 1855 个商品中 **1782 个有库存、73 个库存为 0** → 这 73 个若在 H5 可下单会被商家拒单，需在 H5 侧同步屏蔽。

### 🔴 2.2 支付通道被小程序 openid 绑定 —— H5 无法交接支付（技术死结）

商家后端的支付是微信服务商 JSAPI，下单时：

```js
const bodyObj = {
  sp_appid: WECHAT_APPID,          // ← 小程序 appid
  sp_mchid: WX_MCHID,              // 1666360946
  sub_mchid: order.subMchId,       // 各门店子商户
  out_trade_no: order.id,
  notify_url: 'https://aistore.xiangbinmeigui.com/v1/orders/pay-notify',
  payer: { sp_openid: openid },    // ← 必须是小程序下的 openid
};
```

`payer.sp_openid` 必须属于 `sp_appid`（小程序）。而 H5 用户登录用的是**服务号** `wx7ae8fa263da38a91` 的 openid，**两者不是同一个 openid**（服务号尚未绑定到微信开放平台，`users.unionid` 为空）。

**结论**：H5 必须保留自己的微信支付（已上线、已验证，含退款与 24h 分账）。
→ 订单同步只能是"**H5 已收款，再告诉商家**"。

> 💡 好消息：这笔订单的收款方本来就是**同一个服务商号 1666360946**，所以资金侧天然是一致的，只是发起支付的技术通道不同。

### 🔴 2.3 鉴权层有一个硬编码后门 —— 必须先告知同事

```js
app.post('/v1/auth/phone-login', (req, res) => {
  const { phone, code } = req.body;
  ...
  if (code !== '888888') {            // ← 只有不等于 888888 时才校验短信
    const r = smsCodes[phone];
    if (!r || r.code !== code) return res.json({ code: 1, message: '验证码错误' });
    delete smsCodes[phone];
  }
  ...
  const openid = 'dev_' + phone;      // ← 并自动创建该手机号用户
```

**任何人提交任意手机号 + `888888` 即可登录，并自动创建用户。**
配套风险：`PUT /v1/orders/pay-success` 只校验订单存在、**不校验是否真的收款**，即可把订单标记为已支付并触发下游分派。

**这两点必须告知同事**：前者是越权登录，后者是「未付款即可派单给花店」，属于**资损风险**（花店会真去备货配送）。
在修掉之前，订单同步通道要严格限制在**服务端内部调用**，绝不能把这两个接口暴露给公网。

## 3. 推荐方案架构

**H5 独立收款 + 订单单向投递 + 状态双向同步 + 退款人工审核**

```
┌──────────────┐     ① 用户付款（H5 自有微信支付，服务商 JSAPI）
│   H5 用户端   │ ────────────────────────────────────────────┐
│  (Vue3 SPA)  │                                             ▼
└──────┬───────┘                                   ┌──────────────────┐
       │ ② 订单/状态查询（同域 /api/*）                │  微信支付平台      │
       ▼                                            │  服务商 1666360946 │
┌──────────────────────┐  ③ 支付回调验签             └──────────────────┘
│  twlh5-api (:4000)   │ ◀──────────────────────────────────────┘
│  h5_shop @3307       │
│  ★ 订单唯一权威       │  ← H5 自己的订单主库，含退款/分账
└──────────┬───────────┘
           │ ④ 服务端内网投递（127.0.0.1:3456，带服务令牌）
           │    POST /v1/orders/create → PUT /v1/orders/pay-success
           ▼
┌──────────────────────────────────────────────────────────┐
│  flower-shop (:3456)  ·  flower_shop @3306                │
│  ├─ orders 表（商家视角的同一笔订单）                        │
│  ├─ 下游① → xcx.xiangbinmeigui.com 分派到门店 ★履约通道     │
│  ├─ 下游② → 企业微信群机器人 通知商家 ★商家"收到"订单         │
│  └─ /v1/merchant/* ← 商家后台 admin/ 接单、改状态、审退款     │
└──────────────────────────────────────────────────────────┘
           ▲
           │ ⑤ 状态回捞（H5 轮询 /v1/orders/detail?id=，该接口无需鉴权）
           └──────────────────────────────────────────────────
```

### 职责边界（务必写进评审结论）

| 事项 | 归属 | 说明 |
|---|---|---|
| 收款 / 退款 / 分账 | **H5** | 服务商模式下 H5 已跑通；商家后端的分账开关必须保持 **关闭** |
| 订单主数据（用户视角） | **H5** | `h5_shop.orders` |
| 订单履约（商家视角） | **商家后端** | `flower_shop.orders`，由 H5 投递后成为商家的唯一工作单 |
| 商家通知 / 门店派单 | **商家后端** | 复用现有企业微信 + 跳舞兰平台管道 |
| 退款审核 | **H5（先）→ 商家后台（后）** | 见 §4 |
| 退款执行 | **只能 H5** | 见 §4，绝不能两边都退 |

> 🔴 **财务红线：绝不能双重分账。** H5 已按 10% 佣金做延迟 24h 分账；商家后端的 `ENABLE_PROFIT_SHARING` 当前被 systemd 的 `Environment=` 覆盖为 `false`（这层覆盖关系很脆），必须显式确认并写进运维文档，否则同一笔订单会被分两次账。

## 4. 退款人工审核放在哪里（新增需求）

### 4.1 现状：H5 退款是一条直通链路，没有任何审核

`server/src/orders.js` 的 `POST /api/orders/:id/refund`：

```
① 原子占位（paid/making/delivering/refund_failed → refunding，只有 affectedRows>0 的那次继续）
② 立刻调 refundOrderCore → 直接打微信退款 API
③ 按微信返回如实落库（refunded / refunding / refund_failed）
```

用户点一下，钱就出去了。**切口很清楚：把 ② 从用户端拆出去**，用户端只做 ①，然后停在"待审核"。

### 4.2 建议新增独立状态，不要复用 `refunding`

`refunding` 现在的语义是「**已通过、正在退**」，用户看到"退款中"。审核阶段必须区分开，否则用户以为钱在路上、其实还在排队等人点，运营也分不清一单卡在审核还是卡在微信。

建议新增 **`refund_applying`** → 前端显示「**退款审核中**」，并给明确预期（如"我们将在 24 小时内处理"）。

### 4.3 审核入口放哪：三个选项

| 方案 | 入口 | 优点 | 关键顾虑 |
|---|---|---|---|
| **A. 商家后台（现成的）** | `/opt/flower-shop/admin` **已经有**「同意退款 / 拒绝退款」按钮，调 `PUT /v1/merchant/order/refund-approve` / `refund-reject`，且按门店隔离权限（只能动自己店的单） | **零开发**；商家是履约方，最清楚花是否已制作/已配送；小程序用户走的正是这套流程，商家团队已经熟悉 | 🔴 **它自己会调微信退款**：退款单号 `'RF'+id`、金额用它的 `totalPrice`、用的是商家后端的证书 → 与 H5 的退款能力**直接撞车、会重复出账**。要用它**必须请同事改成"仅标记审核结果、不调退款"** |
| **B. H5 侧自建审核（建议先做）** | 在 `twlh5-api` 加一个受保护的运营审核接口 + 极简审核页 | 退款能力（`refundOrderCore`）本来就在 H5，**金额与退款单号口径完全自控**；不依赖同事改代码；风险最低 | 需要做一个界面；审核人离履约现场远，判断"能不能退"的信息较少 |
| **C. 两层审核** | 商家审"业务可不可退"，H5 运营审"资金放不放" | 最严谨 | 两个界面、两条链路，最慢 |

### 4.4 推荐落地路径

**第一步（现在就能做，只改 H5，不依赖任何人）—— 方案 B**

- `POST /api/orders/:id/refund` 改为：只做原子占位 → 写 `refund_applying` + 退款原因/申请金额 → 返回「已提交，等待审核」
- 新增 `POST /api/admin/orders/:id/refund/approve` 与 `/reject`（独立管理员令牌鉴权）
  · **approve 才调 `refundOrderCore`** —— 现有 ③ 的落库逻辑可以原样复用，改动极小
  · reject 则回写订单为可继续履约的状态，并把拒绝理由透给用户
- 审核页：极简列表（待审核 / 已通过 / 已拒绝）+ 订单快照 + 金额 + 用户填写的原因

**第二步（订单同步进商家后端之后）—— 把审核入口前移到商家后台**

- 但**前置条件**：必须先请同事把 `refund-approve` 改成**只标记审核结果、不执行微信退款**
- 退款执行权**统一留在 H5**（钱是 H5 收的，退款单号必须是 H5 的 `'R'+订单号`）
- H5 轮询或接收商家审核结果 → 由 H5 执行退款

### 4.5 三个必须一起定的规则（否则审核会变成新的扯皮源头）

1. **审核时限**：建议 24 小时内处理。超时策略需产品拍板 —— 自动通过（护用户，但可能被薅）或自动拒绝（护商家，但用户会投诉）。
2. **状态互斥**：审核期间订单不允许被分派/履约；已同步给商家的订单发起退款时，要**反向通知商家停止履约**（现有管道里没有这个反向通知，需要补）。
3. **审核权限**：H5 侧审核人要有独立管理员凭据。现有 `/api/pay/ps/*` 用的是 `X-PS-Token`，可参照其做法但**不要复用同一个令牌**（那是运维接口的凭据）。

## 5. 阶段一：不改对方代码，先打通（建议 2~3 天）

1. **H5 服务端新增投递模块** `server/src/merchantBridge.js`
   - 取用户手机号 → `POST http://127.0.0.1:3456/v1/auth/phone-login` 换取 token（过渡期方案，见下）

   - `PUT /v1/orders/pay-success`：`{ id }` → 触发分派与商家通知

2. **H5 订单表新增同步字段**：`merchant_order_id` / `merchant_sync_state` / `merchant_sync_error` / `merchant_status`
3. **状态回捞**：用户打开订单详情时拉一次 `/v1/orders/detail?id=`，把商家状态映射进 H5 订单页（`pending`→已接单 … `completed`→已完成）

## 6. 阶段二：请小程序同事配合的 5 件事（可直接转发）

> 建议以"接口变更需求单"形式提出，逐条给理由。

1. **新增服务间内部接口**（最重要）
   新增 `POST /v1/integration/orders/accept`，用固定服务令牌（请求头 `X-Service-Token`，与 IP 白名单 `127.0.0.1` 双重校验）鉴权，替代「借道 `phone-login` + `pay-success`」。
   入参建议：`{ externalOrderNo, shopId, items[], amount, paidAt, address, remark, cardContent }`，返回 `{ merchantOrderId }`。
   理由：H5 与商家后端同机部署，需要一个**不依赖用户态登录**的可信通道。

2. **退款审核接口改为「只标记、不退款」**
   `PUT /v1/merchant/order/refund-approve` 目前会**自己调微信退款**（单号 `'RF'+id`、金额取 `totalPrice`、用商家证书）。请改为仅把订单标记为"审核通过"，**资金操作交由 H5 执行**。
   理由：同一笔订单被两个系统各退一次 = 重复出账；且两边退款单号规则不同，微信侧不会去重。

3. **支持「外部已收款」语义**
   现有 `pay-success` 无法区分"H5 已收款"与"真的收到了微信支付"。请在内部接口上显式区分，并对公网 `pay-success` 增加来源校验。
   理由：当前任何知道订单号的人都能把订单标记为已支付并触发派单，存在资损风险。

4. **移除 `888888` 万能验证码**
   理由：任意手机号可越权登录；且会向 `users` 表写入 `dev_<手机号>` 脏账号。

5. **统一满减规则 / 明确价格权威源**
   目前两边满减档位不同（商家三档、H5 一档）。请确认以哪一套为准；若以商家为准，请告知是否会把该规则同步给其他渠道。
   另请确认 `/v1/flowers/list` 返回的 `price` 与实际结算价一致。

### 另需同步确认的四件事（非阻塞）
- 商家后端的**分账开关**当前实际为 `false`，请确认这是长期状态（避免与 H5 双重分账）。
- **库存为 0 的商品**（实测 73/1855）在 H5 会被商家拒单，请确认口径（H5 侧屏蔽 or 对方放宽校验）。
- 分派到门店后**超时未接单**如何处理？建议约定自动退款时限（如 2 小时），否则用户钱扣了、花没送到。
- H5 结算页「自提门店」目前是硬编码，需与商家门店实际清单对齐后再上线自提。

## 8. 验收标准

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | H5 订单在商家后台可见 | `/admin` 订单列表出现该单，门店/商品/收货信息正确 |
| 2 | 商家群收到通知 | 企业微信群出现该订单消息 |
| 3 | 门店收到派单 | `orders.raw.danceOrchidSync.status = 'success'` 且有 `externalOrderId` |
| 4 | 金额一致 | H5 实付 == 商家后台 `total_price` == 分派 `data` 金额（含满减口径一致） |
| 5 | 状态双向同步 | 商家改状态后，H5 订单页 60s 内同步显示 |
| 6 | **退款需人工审核** | 用户申请后订单进入「退款审核中」，**微信侧无任何退款单产生**；运营/商家审核通过后才出现退款单 |
| 7 | **退款只出账一次** | 同一订单在微信侧**只有一条退款记录**，退款单号为 `'R'+订单号` |
| 8 | 退款金额正确 | 退款金额 == H5 实付金额（不是商家重算的 `totalPrice`） |
| 9 | 退款后停止履约 | 退款申请提交后，商家侧订单不再可被派单/继续履约 |
| 10 | 无双重分账 | 同一订单在 H5 与商家后端**只出现一次**分账记录 |
| 11 | 幂等 | 重复投递同一订单不产生两条商家订单 |

## 9. 风险与回滚

| 风险 | 影响 | 应对 |
|---|---|---|
| 满减口径不一致 | 用户实付 ≠ 商家所见，退款金额错 | §2.1：H5 对齐三档 + 投递后金额校验，不一致直接拦截 |
| **退款被两个系统各退一次** | **资损，且难追回** | 🔴 退款执行权**只能**在 H5；商家侧 approve 必须先改成"只标记不退款"；退款单号统一为 `'R'+订单号` |
| 双重分账 | 资损 | 硬性关闭商家后端分账；上线前双人复核 |
| 门店未接单 | 用户已付款但无人履约 | 约定超时自动取消+退款；H5 侧显示"等待商家接单"并给客服入口 |
| 库存为 0 商品被拒单 | 用户下单失败，体验受损 | H5 侧同步屏蔽；或请对方放宽校验 |
| 商家后端重启 | H5 商品链路同时中断（它是 H5 商品源） | 投递失败进重试队列；重启后自动补投 |
| 借道后门被封闭 | 阶段一通道失效 | 阶段二服务令牌上线后再转正式；保留手动补偿入口 |
| 审核引入新瓶颈 | 用户等待变长、投诉上升 | 明确 24h 时限与超时策略；审核页给出一眼可判的信息 |

**回滚**：同步是**附加能力**，不改变 H5 现有订单与支付主流程。出现问题时把投递开关（建议 `MERCHANT_BRIDGE_ENABLED`）置 `false` 即可完全回到现状，H5 订单流程不受影响。
