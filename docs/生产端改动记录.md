## 2. 为什么这样设计

**核心原则：渠道是「事实标签」，不是「分支条件」。**

`source` 字段唯一的用途是回答「**这单的钱归谁管**」。它绝不能被写成 `if (h5) {...} else {...}` 两套资金流程 —— 那会让资金逻辑分裂在两个仓库，改一处忘一处，且 H5 单在商家点同意后钱不会动、H5 又不知道审核过了，整单卡死。

资金永远只在 H5 出账（H5 收的钱），商家侧只负责**决策**（审不审过）与**履约**（做花、送花）。

## 4. ✅ 已解决：城市维度（曾是开启桥接的硬阻塞）

> **状态：2026-09-18 18:00 已解决并上线验证。** H5 侧做了三件事：
> 1. 新增 `GET /api/cities`；`/api/home`、`/api/flowers`、`/api/shops`、`/api/search` 全部支持 `city` 参数（缓存 key 含城市）。
> 2. 首页加城市选择器（`src/components/CityPicker.vue`）+ 城市状态持久化；AI 顾问返回的商品卡按城市过滤（两条渲染路径都覆盖）。
> 3. 🔴 **下单前城市闸门**（`server/src/cityGuard.js`）：`POST /api/orders` 里校验「收货城市 == 门店城市」，
>    不匹配返回 **409 + `code:'CITY_MISMATCH'`**，文案直接告诉用户切到哪个城市 ——
>    这比"让商家拒单"好得多，因为**用户还没付钱**。
>
> 实测：福州商品 + 深圳收货地址 → **409 拦住**；同城 → 200 正常下单。
> 另：实测 `?city=福州` → 202 款、`?city=深圳市` → 0 款；**深圳没有门店**（12 店 / 11 城），
> 所以深圳用户会看到「暂未开通配送」并被引导切换城市 —— 这是预期行为，需产品侧知悉。

本节以下保留当时的原始分析，作为背景。

生产端当时已就绪，但**不能立刻打开 H5 侧的订单投递开关**，因为发现一个新的阻塞项：

### H5 没有「城市」维度，会被商家后端的跨城校验拒单

商家后端 `orders/create` 里有硬校验（`server.js:2101-2116`）：

```js
if (!shopAndAddressCitiesMatch(orderShop, orderAddress)) {
  return res.json({ code: 3,
    message: `该商品由${shopCity}门店配送，当前收货地址为${addressCity}，暂不支持跨城市配送。
              请返回首页切换至${addressCity}后重新选择商品` });
}
```

报错文案里的「请返回首页**切换至 XX 市**」说明**小程序的正常流程是先选城市、再按城市筛选门店与商品**。

而 H5 侧现状：

- `server/src/store.js::storeAllFlowers()` → 调 `/v1/flowers/list`，**不传 city**
- `server/src/store.js::storeAllShops()` → 调 `/v1/shops/list`，**不传 city**
- `src/pages/Checkout.vue` → `shopId` 取购物车**第一个商品的 shopId**，**完全不校验城市**

商家后端的接口本身**支持** city 参数（`/v1/shops/list?city=` 见 `server.js:1944-1948`、`/v1/flowers/list?city=` 见 `:4033-4039`），所以能力是现成的，是 H5 侧没用。

**后果**：若现在开启桥接，用户（如深圳）买到舟山门店（s001）的花 → H5 收款成功 → 投递给商家 → **被拒单**。用户钱已付、商家收不到，比现在更糟。

**可选方案**（需产品拍板）：

| 方案 | 说明 | 影响 |
|---|---|---|
| A. H5 按城市筛选 | 首页/商品列表/AI 推荐全部按用户城市过滤，与小程序行为对齐 | 一致性好，但 H5 可售商品会减少到单一城市 |
| B. 桥接时按城市挑门店 | H5 不限城市展示，但投递前若城市不匹配则记 `sync_failed` 并走人工 | 改动小，但会产生需人工兜底的失败单 |
| C. 请对方放宽跨城校验 | 要求商家后端部署放行 | 涉及真实履约能力，可能性低 |

建议 **A**（与小程序体验一致，从源头消除失败单）。

另有 **73 个库存为 0 的商品**需在 H5 侧屏蔽（否则推过去也会被拒），见 `docs/商家订单桥接-实现说明.md`。

> ✅ **更正（2026-09-18 实测）**：这条在这条通道上**不成立**。H5 商品来自 `/v1/flowers/list`，
> 而该接口返回值里 **库存 ≤ 0 的商品已经是 0 个**。那个「73/1855」是另一个端点的口径。
> 即：H5 当前商品源**不需要额外屏蔽 0 库存**。

## 6. 与 H5 侧开关的关系（务必配套）

> **当前状态（2026-09-18 18:07）：两个开关均已打开，投递通道 = 服务令牌。**
>
> ```
> MERCHANT_BRIDGE_ENABLED=true
> MERCHANT_BRIDGE_BASE=http://127.0.0.1:3456        # 生产商家后端
> MERCHANT_BRIDGE_SERVICE_TOKEN=<64 位>              # 见 §8
> MERCHANT_BRIDGE_AMOUNT_GUARD=warn
> MERCHANT_REFUND_REVIEW_ENABLED=true
> ```
> 开启前的安全检查：`merchant_sync_state IS NULL AND status IN ('paid','making','delivering','completed')` 的订单数 = **0**
> —— 确认补偿扫描器不会把历史测试单补投给真实商家。

H5 侧两个开关的作用：

| 开关 | 作用 | 打开后 |
|---|---|---|
| `MERCHANT_BRIDGE_ENABLED` | 订单投递 + 退款申请投递 + 状态回捞 | H5 新单会真实流向商家（含企微通知与门店派单） |
| `MERCHANT_REFUND_REVIEW_ENABLED` | 用户申请退款只占位、等商家审核 | 用户端不再"申请即退款" |

🔴 **两个必须同时打开。** 只开桥接不开审核时：H5 侧仍是"申请即退"出账，而商家侧因为走了 H5 分支不会改状态 → 商家后台会积压一批永远停在「退款中」的单。

## 8. 第 2 轮（2026-09-18 18:07）：新增服务间登录通道

### 8.1 为什么必须做

H5 订单桥接此前靠 `/v1/auth/phone-login` 里这行取 token：

```js
if (code !== '888888') {   // ← server.js 原第 1799 行：硬编码短信绕过
```

这是**外部审计标记过的安全漏洞**（任意手机号可登录取 token）。同事一旦修掉它，
**H5 订单投递会静默中断** —— 用户付了钱、商家收不到单，且没人会立刻发现。

✅ 关键事实：桥接侧**本来就已**在每个请求上发 `X-Service-Token`（`merchantBridge.js::mfetch`），
缺的只是商家后端那一半 —— 它当时**完全没有** `X-Service-Token` 这个概念。

### 8.2 改了什么（1 处新增，**未改动任何既有代码**）

| # | 文件 | 位置 | 改动 |
|---|---|---|---|
| 1 | `flower-shop/server.js` | 紧邻 `app.post('/v1/auth/phone-login', ...)` **之前** | **新增**端点 `POST /v1/auth/service-login`（含 3 个辅助函数） |

新增文件：`/opt/flower-shop/service-token.txt`（`root:flowerapp`、`0640`、64 位 hex）。
字节数：`263377 → 265929`。

**为什么是"新增独立端点"而不是"改 phone-login 那一行"**：
后者只改 1 行、更省事，但**仍然绑在 phone-login 上** —— 同事重构或删除该接口时照样断。
新端点与它完全解耦，同事修 888888 漏洞时根本碰不到。

### 8.3 安全设计（四道）

1. **来源必须回环**：`req.socket.remoteAddress` 必须是 `127.0.0.1` / `::1` / `::ffff:127.0.0.1`
2. **令牌定时安全比较**：`crypto.timingSafeEqual`（先比长度，避免抛异常）
3. **失败关闭**：密钥文件缺失/为空 → 该端点**一律 403**
4. **密钥与对方配置分离**：独立文件，不污染 `config.json`

签发流程**照抄 phone-login**（`userTokens` + `rememberUserSession` + `writeData({mode:'snapshot'})`），
因此 `orders/create` 的 `getUserAuthRecord(token).openid` 行为**完全一致**，对下游透明。

### 8.4 H5 侧配套改动

`server/src/merchantBridge.js::merchantToken()`：有服务间令牌时走 `/v1/auth/service-login`，
否则退回 `/v1/auth/phone-login`。**并且登录失败会大声报警**（不再静默）：

```
【投递通道断了】商家侧登录失败 /v1/auth/service-login :: forbidden
（服务令牌通道失效：确认商家后端已打 service-login 补丁，且 /opt/flower-shop/service-token.txt
  与 MERCHANT_BRIDGE_SERVICE_TOKEN 完全一致）
```
