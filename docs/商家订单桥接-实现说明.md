# 商家订单桥接 · 实现说明

> 实现时间：2026-09-18｜代码：`server/src/merchantBridge.js`（新增）+ `pay.js` / `index.js`（各一处接线）
> 目标：**H5 已收款的订单投递进商家后端的订单管道**，从而自动获得商家的企业微信通知与门店派单。
> 状态：**已实现、已部署（开关默认关闭）、已实测通过**。退款用户流程尚未接线（见 §7）。

---

## 1. 一句话原理

H5 与商家后端在同一台机器上。H5 收款成功后，由服务端内网调两下：

```
① POST /v1/orders/create   { source:'h5', shopId, items[], address, ... }   → 生成商家侧订单
② PUT  /v1/orders/pay-success { id }                                        → 告知"已收款"
        ↓ 商家后端自动做（我们零开发）
   ③ 企业微信群机器人 → 商家实时收到订单
   ④ POST xcx.xiangbinmeigui.com → 分派到门店（真实履约）
        ↑ H5 侧
   ⑤ GET /v1/orders/detail?id= → 回捞履约状态，向前同步到 H5 订单页
```

**从不调用 `pay-prepare`** —— 商家后端的支付绑小程序 openid，H5 无法交接支付，资金始终由 H5 自己收。

## 4. 关键的三个设计决策

### ① 传 `source: 'h5'` —— 让商家后端知道"这单的钱不归我管"

商家侧据此对 H5 单**跳过微信退款**，避免同一笔订单被两个系统各退一次。详见 `docs/退款审核与订单同步-实施方案.md` §9。

### ② DIY 效果图必须转成绝对 URL

H5 的 DIY 效果图是相对路径（`/agent/generated/xxx.png`），而商家后端的 `getDanceOrchidProductImage()`
只对**绝对 URL 原样透传**，相对路径会被它拼到自己的 `publicBaseUrl`（aistore）上 —— 那是错的。
所以桥接在投递前统一转成 `https://h5.tiaowulan.com/...`。

### ③ 三层失败兜底，绝不影响"钱已收"

订单投递是**附加能力**。任何失败都不能影响支付落库：

| 层 | 机制 |
|---|---|
| 调用方式 | `notifyOrderPaid()` 用 `setTimeout` 脱离支付事务；外层 `try/catch` 只记日志 |
| 幂等 | 以 H5 订单号为商家订单 id（商家侧 `ON DUPLICATE KEY` 天然去重）+ `merchant_sync_state` 状态机 |
| 补偿 | 每 5 分钟扫描一次失败/漏投的订单自动重试（上限 5 次） |

## 7. 退款人工审核接线（已实现，开关默认关闭）

`MERCHANT_REFUND_REVIEW_ENABLED=true` 时，用户端退款从「申请即退款」变成「申请 → 商家审核 → H5 执行」。

| 环节 | 实现 |
|---|---|
| 用户申请 | `POST /api/orders/:id/refund` → 原子占位 → **`refund_applying`（refund_amount 已记，资金未动）**，并记 `refund_prev_status` |
| 送审 | 调 `submitRefundRequest()` 投递商家（商家侧置 `refunding`，后台出现待审） |
| 审核通过 | 商家后台点「同意」→ 商家侧只写 `refundAudit={status:'approved'}`、**不调微信**；H5 的回收任务读到后由 **H5 执行微信退款**（唯一出账点） |
| 审核拒绝 | 商家侧写 `refundAudit={status:'rejected', reason}`；H5 把它恢复成 `refund_prev_status`，金额归零，理由透给用户 |
| 回收 | `reconcileRefundReviews()` 每 3 分钟扫一次 `refund_applying` 的订单（`index.js` 启动） |
| 运营兜底 | `GET /api/orders/admin/refund/pending`、`POST .../approve`、`POST .../reject`；头 `X-Refund-Token`；**未配 `MERCHANT_REFUND_ADMIN_TOKEN` 时整组 404** |

### 🔴 修掉的一个致命 bug（教训值得记）

运营兜底接口最初的守卫写法是「守卫里发 401，调用处再补一次 404」——
结果**未授权请求会把整个 H5 API 打崩**：

```
Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client
    at orders.js:499 → process exit(1) → systemd 自动重启
```

**规则：一个既发响应又返回布尔值的守卫，调用处只能写 `if (!guard(req,res)) return`，绝不能再补一次响应。**
修复后实测：无令牌 / 错令牌 / 对令牌 三种情况各自正确返回，且进程 `NRestarts` 保持为 0。

### 🔴 第 8 项：为什么它是硬阻塞

商家后端 `orders/create` 有硬校验 —— 收货城市必须等于门店服务城市（`/opt/flower-shop/server.js:2101-2116`），报错文案是「该商品由 XX 门店配送……**请返回首页切换至 YY 市**后重新选择商品」。

这说明**小程序的正常流程是「先选城市 → 再按城市筛选门店与商品」**。商家后端的接口本身支持 city 参数（`/v1/shops/list?city=` `:1944`、`/v1/flowers/list?city=` `:4033`），**能力是现成的**。

而 H5 侧完全没用：

- `server/src/store.js::storeAllFlowers()` / `storeAllShops()` → 拉**全国**数据，**不传 city**
- `src/pages/Checkout.vue` → `shopId` 取购物车**第一个商品的 shopId**，**不校验城市**

**后果**：用户（如深圳）买到舟山门店（s001）的花 → H5 收款成功 → 投递商家 → **被拒单**。用户钱已付、商家收不到，比现在更糟。

**可选方案**（需产品拍板，详见 `docs/生产端改动记录.md` §4）：

| 方案 | 说明 |
|---|---|
| **A. H5 按城市筛选**（建议） | 首页/列表/AI 推荐全部按用户城市过滤，与小程序一致；改动中等，从源头消除失败单 |
| B. 投递时按城市挑门店 | H5 不限城市展示，投递前不匹配则记 `sync_failed` 走人工；改动小但会产生需人工兜底的失败单 |
| C. 请对方放宽跨城校验 | 涉及真实履约能力，可能性低 |

> 建议顺序：**先解决第 8 项** → 在测试端（3457）跑通真实业务流程 → 再切 `MERCHANT_BRIDGE_BASE=http://127.0.0.1:3456`。
