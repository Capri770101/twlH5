# flower-shop 独立测试实例 · 使用说明

> 建立时间：2026-09-18｜位置：`129.204.85.139`｜**目的：让 H5 订单接入联调可以在完全不惊动真实商家的前提下跑通。**

---

## 1. 为什么不是"在生产后台加一个测试门店"

最初的想法是直接在商家后端里加一个测试门店，但实测发现**这样会污染线上**：

| 检查项 | 实测结果 | 后果 |
|---|---|---|
| `/v1/shops/list` 的可见性过滤 | 只判断 `status !== 'closed'`，**没有隐藏/测试标记** | 测试门店会出现在 C 端门店列表中，**真实用户能看到** |
| 企微订单通知 | `WECOM_ORDER_WEBHOOK` 是**全局单一 webhook**，没有按门店区分 | 测试订单会推送到**真实商家群** |
| 门店派单 | `order-integration.json` 逐店配置，未配置则跳过 | ✅ 这一项天然安全 |

而如果为了隐藏把测试门店设成 `status='closed'`，`orders/create` 的 `isShopAcceptingOrders()` 又会直接拒绝下单 —— **隐藏和可下单互相冲突**。

所以改为**独立实例**：同一个后端程序，完全独立的数据库、配置与端口。零污染、零外部依赖，也不需要同事改代码。

| # | 隔离手段 | 效果 | 验证方式 |


## 5. 联调怎么用

H5 后端的桥接模块（待实现）只需一个可配的基地址：

```bash
# H5 /opt/twlh5-api/.env
MERCHANT_BRIDGE_ENABLED=true
MERCHANT_BRIDGE_BASE=http://127.0.0.1:3457   # 测试实例
# MERCHANT_BRIDGE_BASE=http://127.0.0.1:3456  # 生产（确认后才切）
```

联调闭环：

```
① H5 下单（测试门店 ts001）
② H5 服务端投递 → 127.0.0.1:3457
      POST /v1/orders/create  +  PUT /v1/orders/pay-success
③ 到 http://127.0.0.1:3457/admin 用 13900000001 / 888888 登录
      → 应该能看到这笔订单，并能改状态 / 点退款审核
④ 回捞：GET http://127.0.0.1:3457/v1/orders/detail?id=<单号>（无需鉴权）
      → 拿到商家侧状态，回写 H5 订单页
⑤ H5 侧执行退款（资金动作只在 H5）
```

**验证要点**：全程不会出现在 C 端门店列表、不会推真实商家群、不会派单到真实花店、不会调微信支付。

## 7. 注意事项

- ⚠️ **测试实例与生产实例共用同一份前端商品源语义**：H5 的商品接口仍指向生产 `aistore`。做订单联调时，H5 侧的商品 id 若要落到测试门店，需要在测试库里也存在同样的商品 id，或直接用 `tf001/tf002` 测试。
- ⚠️ 测试实例的 `subMchId` 是占位值 `1700000001`，**不要**尝试走真实支付（会失败，属于预期行为）。
- ⚠️ 测试实例**没有** `admin` 的独立副本差异 —— 它服务的是 `/opt/twlh5-test/admin`（从 `/opt/admin` 复制）。生产后台界面若更新，测试副本不会自动跟随。
- ⚠️ 服务器上存在两个 admin 目录，**线上真正生效的是 `/opt/admin`**（`server.js` 里写的是 `path.join(__dirname,'..','admin')`）。`/opt/flower-shop/admin` 是另一个旧副本，改动它不会生效。

## 8. 能力边界：测试端到底能做什么、不能做什么（已实测）

这是最容易误解的一点。测试端的定位是「**验流程，不验钱**」。

| 环节 | 测试端 | 实测证据 / 说明 |
|---|---|---|
| 下单 | ✅ **真能** | 真写进测试库（`202609180006`，用**真实商品 id** 也下单成功） |
| 商家后台看到订单 | ✅ 真能 | 后台功能完整可用 |
| 商家改状态（接单/制作/配送/完成） | ✅ 真能 | |
| 用户申请退款 | ✅ 真能 | `PUT /v1/orders/refund` → 状态 `refunding` |
| 商家审核（同意 / 拒绝） | ✅ 真能 | 流程完整走通 |
| **真实收款** | ❌ **故意不能** | `POST /v1/orders/pay-prepare` 被拒绝（没有支付证书） |
| **真实退款出账** | ❌ **故意不能** | ⚠️ 见下方警告 |

### 🔴 一个必须知道的陷阱：没有证书时它会「假装退款成功」

实测商家点「同意退款」后的返回：

```
{"code":0,"message":"退款处理成功"}
订单状态 → refunded（退款成功）
refundNo → NULL          ← 没有产生任何真实退款单号
```

**它不报错，而是直接把订单标记为已退款。** 所以：
- 测试端适合验证**流程与状态流转**
- 但「钱有没有真的退回去」这一步在测试端**是假的**，不能当作资金验证

### 那测试时怎么模拟「用户已付款」

**直接调 `PUT /v1/orders/pay-success` 标记为已收款即可。** 这正好就是 H5 桥接要调的那一步，所以**不需要真钱**。

### 关键澄清：测试端能不能收款，其实不影响我们

**H5 的收款永远走 H5 自己的支付通道，从来不调用商家后端的支付接口。** 商家后端的付款能力（`pay-prepare`，`sp_appid` = 小程序 appid）我们根本不用 —— 这正是 §2.2 里说的「支付不能交接」。

所以：
- **流程逻辑 100% 可以在测试端验完**（下单 → 商家可见 → 状态流转 → 退款审核 → 回捞）
- 「真实收款 / 真实退款」是 H5 自己的事，与测试端无关

### 如果要验真实的收款+退款

只有两条路：
1. **用真实门店下一笔小额真实订单**（会真实触发：商家群收到通知、门店收到派单）→ 只在最终验收做**一次**，且必须提前知会商家
2. 给测试实例配真实子商户号 + 补上支付证书 → **不推荐**，那会彻底破坏隔离（测试环境就能动真钱了）

## 10b. 生产端改动执行时的注意点（2026-09-18 实战）

- **重启需要等 6 秒左右**才监听端口（要先读全库到内存）。重启后立刻 curl 会拿到 `000`，不是故障。
- 生产文件里混有**历史遗留的乱码注释**（GBK 误存的 `// 璋冪敤寰俊...`）。补丁用**字节级锚点**替换，天然绕开。
- 该后端统一用 **body 里的 `code` 表达错误**（HTTP 状态码仍是 200）。所以"鉴权拦截"表现为 `HTTP=200` + `{"code":401,...}`，**不要误判为鉴权失效**。
- `/v1/banners/list`、`/v1/categories/list` **本身就不存在**（返回 404 属正常）。H5 实际用的是 `/v1/home/index`。
- 商家站点域名是 **`aistore.xiangbinmeigui.com`** / **`aiadmin.xiangbinmeigui.com`**（不是 `.tiaowulan.com`，后者无 DNS 记录）。
