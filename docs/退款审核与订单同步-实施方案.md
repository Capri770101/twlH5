# H5 退款审核与订单同步 · 实施方案

> 目标：① 把 H5 真实订单送到商家（打通业务链路）；② 给退款加上人工审核。
> 前置阅读：`docs/H5接入商家后端-订单同步方案.md`（商家后端勘查与接口事实）
> 结论：**先做 H5 侧退款审核（0 外部依赖），订单投递紧随其后。**

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 订单现在到商家了吗 | 没有。只落在 `h5_shop.orders`，商家库中 H5 订单数 = 0 |
| 退款怎么做 | **决策与执行分离**：谁决定"退不退" ≠ 谁执行"退钱"。决策可以换人，**执行只能有一个** |
| 要不要在商家后端区分小程序 / H5 | **要，但只加一个「订单来源」字段**（用途：让商家后端别碰 H5 单的资金）。**绝不要**在退款逻辑里写 `if (h5) {} else {}` 两套流程 |
| 先做哪一步 | **H5 侧退款审核** —— 不依赖同事改代码，1~1.5 天可上线，直接堵住"点一下就退钱"的风险 |
| 商家能参与退款决策吗 | 能，但**需要同事改一处**（让商家后端的退款接口不再自己调微信）。作为第二阶段 |

## 1. 为什么必须走"分权"这条路

有一个绕不过去的技术事实（已实地核实）：**H5 无法把收款交给商家后端**。

商家后端的支付是微信服务商 JSAPI，下单时 `sp_appid` 固定为**小程序** appid、`payer.sp_openid` 必须是小程序下的 openid。而 H5 用户登录拿到的是**服务号**的 openid —— 两者不是同一个 openid（服务号尚未绑定微信开放平台，`unionid` 为空）。

⇒ 所以在整个体系里：

| 关注点 | 权威方 | 理由 |
|---|---|---|
| **收款 / 退款 / 分账（资金）** | **H5** | 技术上只能如此：只有 H5 持有服务号通道与用户 openid |
| **订单主数据（用户视角）** | **H5** | `h5_shop.orders` 已承载用户订单、地址、退款记录 |
| **履约（接单 / 制作 / 配送 / 完成）** | **商家后端** | 商家后台、门店派单、企微通知都已具备 |
| **退款业务决策（该不该退）** | **看谁离现场近** | 见 §3，这是唯一可以协商的一项 |

**关键推论**：既然资金只能 H5 出，那么"退款审核"这件事必须拆成两半 —— **决策**可以在任何地方，**执行**只能在 H5。想清楚这一点，后面的所有设计都顺了。

## 2. 订单怎么送到商家（原目标，最小改动）

### 2.1 原理

H5 后端（`:4000`）与商家后端（`:3456`）在**同一台机器**。所以只需：

```
H5 支付成功
   ↓ 服务端内网调用（127.0.0.1:3456）
① POST /v1/orders/create   → 生成商家订单（校验商品/门店/同城）
② PUT  /v1/orders/pay-success → 标记已收款
   ↓ 商家后端自动触发（现有管道，无需开发）
③ 企业微信群机器人 → 商家实时收到订单
④ POST xcx.xiangbinmeigui.com → 分派到门店（真实履约）
   ↓ H5 侧
⑤ GET /v1/orders/detail?id= → 回捞商家状态，回写 H5 订单页
```

**③④ 是完全免费的** —— 商家后端本来就有，我们只要把订单送进去。

### 2.2 必须同时做的两件小事

1. **满减口径对齐**：商家后端会叠加自己的满减（满 100 减 10 / 满 200 减 20 / 满 300 减 30），而 H5 只有「满 200 减 20」一档。不改的话：¥100~199.99 的单商家会少算 ¥10、≥¥300 的多减 ¥10 → 商家后台显示的金额与用户实付不一致，**退款金额也会错**。
   → 把 H5 的满减改成**同样的三档**（顺带把促销做完整），并在投递后回读商家 `totalPrice` 做一次校验。

2. **库存为 0 的商品要屏蔽**：商家后端要求 `stock > 0`，实测 1855 个商品里 **73 个库存为 0**，这些推过去会被直接拒单。

### 2.3 幂等与容错

- 以 **H5 订单号**作为商家订单 id 与幂等键（商家侧 `ON DUPLICATE KEY UPDATE` 天然支持）
- 投递失败进重试队列，落 `merchant_sync_state` / `merchant_sync_error`
- 总开关 `MERCHANT_BRIDGE_ENABLED`，出问题一键回滚到现状

## 3. 退款怎么做（核心）

### 3.1 把三件事拆开

```
① 申请   → 用户点「申请退款」           ：现在只有这一步，且它直接就把钱退了
② 决策   → 谁批准 / 谁拒绝             ：目前完全缺失 ← 这就是要补的洞
③ 执行   → 调微信退款 API（真正出账）   ：只能在 H5
```

现在 H5 的 `POST /api/orders/:id/refund` 是**一气呵成**的：占位 → 立刻调微信退款 → 落库。**只要把 ③ 从这条链路里摘出来**，审核就有了位置。

### 3.2 状态机（新增 `refund_applying`）

```
        ┌─ 用户申请退款 ─┐
        ↓
  paid / making / delivering / refund_failed
        ↓ ① 原子占位（只有 affectedRows>0 的那次继续）
  ┌─────────────────────┐
  │  refund_applying    │  ← 新增：退款审核中
  │  微信侧无任何动作     │     （此时钱还完全没动）
  └─────────────────────┘
        ↓ ② 人工审核（运营 或 商家）
   ┌────┴─────┐
 拒绝        通过
   ↓          ↓ ③ H5 执行微信退款（唯一出账点）
 回到退款前  refunding → refunded / refund_failed
 的状态
```

### 3.3 ⚠️ 为什么不复用 `refunding`

`refunding` 现有语义是「**已通过、正在退**」，用户看到的是"退款中"。如果审核阶段也用它：
- 用户以为钱在路上，其实还在排队等人点 → 投诉与客诉
- 运营分不清一单是**卡在审核**还是**卡在微信**
- 前端 `Orders.vue` 现有的"退款处理中，请留意到账通知"文案会变成假话

所以必须新增 `refund_applying` → 前端显示「**退款审核中**」，并给出明确预期（如"我们将在 24 小时内处理"）。

### 3.4 三个方案对比

| 方案 | 谁审 | 优点 | 关键顾虑 |
|---|---|---|---|
| **A. H5 侧审核（推荐先做）** | 跳舞兰运营 | 退款能力本来就在 H5；金额与退款单号口径完全自控；**不依赖同事改代码**；改动最小、风险最低 | 要做一个极简审核页；审核人离履约现场远，判断"该不该退"的信息少 |
| **B. 商家后台审核** | 出花门店 | **零开发**（商家后台已有「同意退款/拒绝退款」按钮）；商家最清楚花做了没、送了没；商家团队已在用这套（小程序走的就是它） | 🔴 那个接口**自己会调微信退款**（金额用它的 `totalPrice`、单号 `'RF'+id`、用商家证书）→ 与 H5 **撞车、重复出账**。要用必须请同事改成"只标记不退款" |
| **C. 两层审核** | 商家审业务 + 运营审资金 | 最严谨 | 两个界面两条链路，最慢；只有客诉多时才值得 |

**✅ 已定稿（2026-09-18）：采用方案 B —— 审核交给商家，但资金执行权留在 H5。**
理由：商家是履约方，最清楚花有没有做、有没有送，审核质量最高；而且商家后台的退款审核界面**已经存在**，商家团队在小程序上本来就在用这套流程。
但**必须先把商家后端的退款执行关掉**（否则重复出账），完整协议见 **§9**。
方案 A（H5 侧自建审核）保留为**兜底**：若同事短期内无法配合改代码，先用 A 上线，改造点见 §3.5。

### 3.6 审核页要展示什么（一眼可判，不要点进点出）

- 订单号 / 下单时间 / 支付时间 / **用户申请退款的时间**
- **实付金额** + 用户申请的退款金额（一般是全额）
- **用户填写的原因**（这是决策的主要依据）
- 出花门店 / 商品名称与数量
- **商家侧当前进度**（已接单？制作中？配送中？）← 接入商家后端后，这一项决定了"该不该同意"
- 两个按钮：通过（调 `approve`）/ 拒绝（要求填理由）

### 3.7 三条必须一起定的规则

1. **审核时限**：建议 24 小时内处理。**超时策略需产品拍板**：
   - 自动通过 → 护用户，但可能被恶意薅（尤其花已在配送中）
   - 自动拒绝 → 护商家，但用户会投诉
   - 我的建议：**接近配送完成的单自动转人工 + 超时自动通过**（花没送到的情况下拖着不退最伤口碑）
2. **审核期间禁止履约**：订单进入 `refund_applying` 后不允许被派单/继续制作。已投递给商家的订单，退款申请要**反向通知商家暂停**（现有管道没有这个反向通知，阶段二需补）
3. **谁能审**：必须是独立的管理员凭据，且**操作留痕**（`refund_audit_by` / `refund_audit_time`）

## 4. 「要区分小程序和 H5 吗」—— 要，但只加一个来源字段

你的直觉是对的，关键是**区分出来用来做什么**。

### ✅ 正确做法：加 `source` 字段表示"订单来源"

在商家订单上打一个来源标记（`source: 'mini' | 'h5'`），用途只有三个：

1. **让商家后端知道"这笔单的资金不归我管"** → 对 H5 单**不提供/禁用**它的退款执行（避免重复出账）
2. 商家后台能看出这单来自哪个渠道（运营视图、客服排查）
3. 结算与对账能按渠道分开统计

### ❌ 错误做法：在退款逻辑里写两套流程

如果在商家后端里写成 `if (source === 'h5') { 只标记 } else { 调微信退款 }`，会变成：
- 资金逻辑分裂在**两个仓库**里，改一处忘一处
- H5 单在商家后台点了同意之后，钱不会动（因为商家不执行），H5 又不知道审核过了 → **卡死**
- 未来任何退款规则的调整都要两边同时改，且无法保证一致

### ✅ 正确的心智模型

**渠道是「事实标签」，不是「分支条件」。**
来源字段只回答"这单从哪来"，不决定"钱怎么走"。钱怎么走由 §1 的分权原则决定：**资金永远只在 H5 出**，与渠道无关。

## 5. 三阶段实施计划

### 阶段一：H5 侧退款审核（**先做这个**）
- **依赖**：无外部依赖，只改 H5
- **工作量**：1~1.5 天（含前端文案与审核页）
- **产出**：`refund_applying` 状态 + 审核页 + approve/reject 接口
- **立刻收益**：堵住"用户点一下钱就出去"的风险；退款全程留痕
- **风险**：低。退款执行逻辑一行不改，只是多了个前置闸门

### 阶段二：订单投递打通（你的原目标）
- **依赖**：需要同事确认 §2 的两件小事（满减口径、库存口径）；过渡期可借道现有接口验证
- **工作量**：2~3 天
- **产出**：`merchantBridge` 模块 + `source` 字段 + 状态回捞 + 金额校验
- **里程碑**：一笔真实 H5 订单出现在商家后台、企微群收到通知、门店收到派单

### 阶段三：退款审核前移到商家（增强，可选）
- **前置条件（硬）**：同事把 `refund-approve` 改成**只标记不退款**
- **产出**：商家在后台审 H5 单 → H5 回捞结果 → H5 执行退款
- **价值**：决策交给离现场最近的人，退款纠纷显著减少
- **若对方不愿改**：保持阶段一的方案，商家通过企微群线下沟通，运营在审核页操作（人肉但可用）

## 6. 验收标准（退款部分）

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | 申请后**不产生任何退款单** | 用户在 H5 点申请退款后，微信侧 `trade_state` 不变、无退款单；订单显示「退款审核中」 |
| 2 | 审核通过才出账 | 运营点通过后，微信侧出现**一条**退款单，`out_refund_no = 'R' + 订单号` |
| 3 | 退款金额 == 用户实付 | 不是商家重算的金额 |
| 4 | 同一订单只出账一次 | 重复点通过、并发点通过，微信侧仍只有一条退款单（靠 `'R'+订单号` 幂等 + 原子占位双闸门） |
| 5 | 拒绝可恢复 | 拒绝后订单回到退款前的状态，可继续履约 |
| 6 | 审核留痕 | `refund_audit_by` / `refund_audit_time` / `refund_reject_reason` 有值 |
| 7 | 审核期间不可派单 | 处于 `refund_applying` 的订单不会被投递给商家 |
| 8 | 未登录不可审 | 审核接口无令牌返回 401，前端页面不可访问 |

## 9. 最终设计定稿（2026-09-18）

### 9.1 定稿的三条原则

1. **审核交给商家**（商家是履约方，最清楚该不该退）
2. **资金执行权只在 H5**（钱是 H5 收的；商家后端的支付通道绑小程序 openid，H5 用不了）
3. **不重复出账**（两个系统都能退款是最大的资损风险，必须用协议 + 代码双重锁死）

### 9.2 怎么在同一个后端里区分小程序和 H5

**只加一个「订单来源」字段，用它回答"这单的资金归谁管"。不写两套流程。**

`orders/create` 接收并保存：

```js
// 商家后端 server.js —— orders/create 里给 order 对象加一个字段
source: String(req.body.source || 'mini'),   // 'mini' | 'h5'，默认 mini（兼容存量调用）
```

这一个字段解决三件事：
- 商家后台能看出订单来自哪个渠道
- 结算/对账可按渠道分开统计
- **最关键：退款审核接口据此决定「要不要动钱」**

### 9.3 防重复出账协议（核心）

```
           ┌──────────── H5 侧 ────────────┐   ┌──────── 商家后端 ────────┐
用户申请退款 → H5 原子占位
              status = refund_applying
              （微信侧无任何动作）
                       ↓ 投递退款申请
              PUT /v1/orders/refund { id }  ──→  商家侧 status = refunding
                                                 商家后台出现「待审核退款」
                       ↑                              ↓ 商家点「同意」
              GET /v1/orders/detail?id=  ←──  refundAudit.status = 'approved'
                读到 approved                        （★ source==='h5' 时
                       ↓                              只标记，不调微信）
              H5 执行微信退款（唯一出账点）
              out_refund_no = 'R' + 订单号
                       ↓
              refunded / refund_failed
```

**四道锁**（每一道都独立成立，任一失效仍有其它三道兜底）：

| # | 锁 | 位置 | 作用 |
|---|---|---|---|
| 1 | `source === 'h5'` 时商家侧**不调用**微信退款 | 商家后端 `refund-approve` | 商家侧根本不会出账 |
| 2 | 原子占位（`affectedRows > 0` 才继续） | H5 `POST /:id/refund` | 挡住并发重复申请 |
| 3 | `out_refund_no = 'R' + 订单号` 固定派生 | H5 `refundOrderCore` | 微信侧天然幂等，重复调用只返回同一笔 |
| 4 | 执行前校验订单状态为 `refund_applying` | H5 approve 接口 | 挡住状态错乱的进入 |

### 9.4 需要同事改的三处（都很小）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `orders/create` | 接收并保存 `source` 字段（`String(req.body.source \|\| 'mini')`）。**1 行**，不改默认行为 |
| 2 | `PUT /v1/merchant/order/refund-approve` | 开头加判断：`if (order.source === 'h5') { order.refundAudit = { status:'approved', by, at }; writeData(...); return res.json({code:0, message:'已通过（资金由 H5 执行）'}) }`，**其余逻辑一行不动**（小程序单继续走原来的调微信退款） |
| 3 | `PUT /v1/merchant/order/refund-reject` | 同样写 `order.refundAudit = { status:'rejected', reason, by, at }`；H5 单额外接受可选参数 `restoreStatus`（默认 `paid`）来恢复商家侧订单状态 |
| 4 | `/opt/admin/js/app.js` 的 `getProductPrimaryImage` | 加第二个参数 `orderItem`：**优先返回 `orderItem.image`**，找不到才回退商品库的图（这样商家后台才能看到 H5 传来的 DIY 效果图）。纯静态文件，无需构建 |

> 说明：`GET /v1/orders/detail` 返回的是完整订单对象，`refundAudit` 会自动透出，**不需要额外改**。

> 🔴 **部署提醒**：这三处都在 `/opt/flower-shop/server.js` 里，而该目录**没有 `.git`、也没有部署脚本**。
> 直接改生产那份文件虽然会生效，但同事下次发布会整文件覆盖 → 改动静默消失。
> **正确顺序**：同事改他的源码并发布（权威）；我们**先在测试端**（`/opt/twlh5-test/flower-shop/server.js`）验证设计，通过后再把清单交给他照做。

**建议给同事的原话**：
> 我们在同一个后端里加了 `source` 字段区分渠道。H5 单的资金（收款/退款/分账）由 H5 侧负责，因为服务商支付的 openid 通道绑的是小程序 appid，H5 用户拿不到小程序 openid。
> 所以 H5 单在商家后台点「同意退款」时，请**只记录审核结果、不要调用微信退款**，由 H5 读取审核结果后自己执行。小程序单的逻辑完全不变。
> 这样能避免同一笔订单被两个系统各退一次。

## 10. DIY 效果图随订单传给商家（已抓包验证）

### 10.1 结论：能传，而且机制是现成的，**不需要同事改服务端代码**

商家后端在派单给门店时，本来就会给每个商品带一张图：

```js
// /opt/flower-shop/server.js :: buildDanceOrchidOrderData
products: (order.items || []).map(item => ({
  name: String(item.name || ''),
  num: Number(item.quantity || 1),
  price: centsToYuan(item.price),
  path: getDanceOrchidProductImage(item)     // ← 关键
}))

// 取图逻辑：item.image 优先；已是绝对 URL 就原样使用
function getDanceOrchidProductImage(item) {
  const value = String(item.image || ((item.images || [])[0]) || '').trim();
  if (!value || /^https?:\/\//i.test(value)) return value;   // 绝对 URL 直接用
  const base = String(ORDER_INTEGRATION_CONFIG.publicBaseUrl || '').replace(/\/+$/, '');
  return base && value.startsWith('/') ? base + value : value;
}
```

而 `normalizeOrderItemsForShop()` 用 `...item` 展开，**会原样保留我们传的额外字段**（包括 `image`）。

⇒ **H5 只要把 DIY 效果图的绝对 URL 放进 `items[].image`，它就会一路传到门店。**

### 10.3 三个"看得到 / 看不到"的地方（已实测）

| 位置 | 能否看到 DIY 效果图 | 说明 |
|---|---|---|
| **门店 / 花店**（真正做花的人） | ✅ **能看到** | 通过派单报文的 `products[].path`。**这是最重要的**，因为做花的是花店 |
| **商家后台界面**（`/admin`） | ⚠️ 默认**看不到** | `getProductPrimaryImage()` 只按商品 id 查自己的商品库取图，忽略 `item.image` → 需改 §9.4 第 4 项（3 行，纯静态文件） |
| **企业微信群通知** | ⚠️ **看不到** | `buildWecomOrderMessage()` 是纯文本（只输出「商品名 x数量」）。**零改动**的办法：把图片 URL 拼进 `remark`，群里会出现可点链接 |

### 10.4 H5 侧要做的（待实现，含在桥接模块里）

1. 下单/投递时，把 DIY 效果图 URL 写进 `items[].image`
   - 来源：DIY 卡的 `result_url`（相对路径）→ 用现有 `normalizeAgentAssetUrl` 归一后**再拼成绝对 URL**（`https://h5.tiaowulan.com/agent/generated/xxx.png`）
   - ⚠️ **必须转成绝对 URL** —— 相对路径只有在 `publicBaseUrl`（当前是 aistore）下才成立，而图在 H5 域名下，会拼错
2. 若希望商家群也能看到图，把同一个 URL 追加到 `remark`（如 `remark: '用户自选DIY方案 效果图：<url>'`）
3. 若该 DIY 单没有生成效果图（平台不保证每次都派生图任务），`image` 留空即可 —— 门店侧会退回无图

### 10.5 一个需要注意的边界

派单报文里的 `path` 会指向 **H5 域名**（`h5.tiaowulan.com`）而不是原来的 `aistore` 域名。
- 好处：H5 的 `/agent/*` 反代本身是公开的（图无需鉴权），实测可达
- 风险：如果将来给 `/agent/*` 加了登录校验，**花店就打不开这些图了** → 建议为 `/agent/generated/*` 保留公开可读（或改用对象存储/CDN 承载生成图）
