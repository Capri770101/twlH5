## 五、小程序的分账实现（重点，逻辑可照搬）

**开关**：`ENABLE_PROFIT_SHARING = true`（已开启）

**触发**：订单 `completed` 后**延迟 24 小时**；另有**每 10 分钟**的扫描器做补偿（防重启丢任务）。

**金额**：`floor(订单总额 × 比例%)`，最低 1 分。

**接收方**：`{ type: 'MERCHANT_ID', account: 服务商号, relation_type: 'SERVICE_PROVIDER' }`

**调用链**：

```
① 查单拿交易号
   GET /v3/pay/partner/transactions/out-trade-no/{订单号}?sp_mchid=&sub_mchid=
② 发起分账
   POST /v3/profitsharing/orders
        { appid, sub_mchid, transaction_id, out_order_no:'PS'+订单号,
          receivers:[…], unfreeze_unsplit: true }
   ↳ 若报 RECEIVER_NOT_EXIST → 先 POST /v3/profitsharing/receivers/add 再重试（自愈）
③ 退款前必须回退分账
   POST /v3/profitsharing/return-orders
```

订单上的分账字段：`profitSharing` / `State` / `OrderId` / `Amount` / `ScheduledAt` / `Return*`。

## 七、关于"改用 v2"：可行，但不推荐

**你的 v2 物料是齐全的**（已核验）：

| 文件 | 用途 |
|---|---|
| `wechat_apiv2_key.txt`（32 字符） | v2 接口签名（MD5/HMAC-SHA256） |
| `apiclient_cert.pem` + `apiclient_key.pem` | **v2 分账的强制双向证书** |
| `merchantid.txt` = `1235197102` | 与证书主体一致 |

**v2 确实能绕开 APIv3 密钥**：v2 回调是 XML 明文 + APIv2 密钥验签，不需要 APIv3 密钥。

**但代价不小**：

1. H5 现有支付层是**全面 v3** → 切 v2 等于重写 `wxpay.js` + `pay.js`（签名、XML 报文、下单、查单、关单、退款、回调验签、分账），约 400–600 行；
2. v2 处于**维护期**，微信官方主推 v3；
3. 之前修过的两个 v3 坑（回调被 JSON 解析吞掉、金额可篡改）在 v2 下是**另一种形态**，要重新验证；
4. 前端 `signType` 要从 `RSA` 改回 `MD5`。

**最关键的一点**：

> **`APIv3 密钥` 不是"别人的东西"，而是你在自己的服务商商户平台（1235197102）里自己设的**
> —— 商户平台 → 账户中心 → API 安全 → APIv3 密钥（32 位）。
> 而且 **AppID 授权管理**（把服务号授权给服务商号，否则下单报 `APPID_MCHID_NOT_MATCH`）
> **也只能在商户平台做** —— 这一关 **v2 一样绕不过**。

**所以**：既然必须有人登商户平台，顺手设一个 APIv3 密钥就够了，**0 行代码改动**；改造成 v2 反而把一个"填配置"的问题变成了"重写支付模块"。

| 步骤 | 内容 | 谁做 | 代码改动 |
|---|---|---|---|
| 1 | 商户平台设 **APIv3 密钥**（32 位） | **你 / 财务** | 无 |

| 5 | 移植分账回退（接到退款流程前） | 我 | 有 |
| 6 | 加 24h 延迟调度 + 10 分钟补偿扫描 | 我 | 有 |

**另有一项建议现在就改**：H5 下单目前**无条件**带 `settle_info.profit_sharing=true`，而 H5 还没有分账任务 → 零佣金店的资金可能被白冻结。应改成与小程序一致（**佣金 > 0 才带**）。此项**不依赖任何人**。

## 九、一句话总结

小程序的分账**逻辑是现成的、可以直接照搬**；但两家是**不同的服务商账户**，H5 必须用自己的证书和商户号。
H5 的支付物料本次已补齐，**只剩 `WXPAY_APIV3_KEY` 一项** —— 这一项在商户平台自己设即可，**不需要改造成 v2**。
